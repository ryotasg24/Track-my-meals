## 1. はじめに

### 1.1 目的
食事をiPhoneのカメラで撮るだけで、AIが料理と量を推定し、カロリーと栄養価を記録します。あわせて、次のことができるようにします。

- 1日に摂るべきカロリーと栄養素の目標を、体格と目的（減量・維持・増量）から計算する
- 目標に対して、今日あと何をどれだけ食べてよいか（または控えるべきか）を確認する
- 食事を記録するたびに、AIが「次の食事のおすすめ」を提案する
- 1日が終わったら、AIが前日の結果をふりかえり、「今日の調整案」を提案する
- 体重と、摂取カロリーの推移をグラフで確認する

### 1.2 方式を選んだ理由
PWA（ホーム画面に追加して使うWebアプリ）で作ります。AIには、Googleの「Gemini API」の無料枠を使います（2026-11-07 決定）。

| 観点 | 利点 |
|---|---|
| 開発環境 | Windowsだけで開発できる（Macは不要） |
| 費用 | Apple Developer Programへの登録（年会費）が不要。公開はGitHub Pages（無料）、AIはGemini APIの無料枠を使うため、原則として費用がかからない |
| 配布・更新 | App Storeの審査が不要。サイトを更新すればアプリも更新される |
| 対応端末 | iPhone・iPad・PCのどれでも、ブラウザがあれば動く |
| サーバー | 自分のAPIキーを設定画面に入力し、端末から直接AIを呼び出すため、中継用のサーバーが要らない（2026-11-07 決定） |

この方式による制約（詳細は「7. 制約事項」）：
- AIで読み取るときは、写真と文章をGoogleに送る。無料枠では、送った内容がGoogleのサービスの改善に使われ、人が内容を見る場合がある
- AIの推定は、通信できるときだけ使える
- ヘルスケアから直接データを読めない（ショートカット経由で取り込む）
- iCloudでの自動同期ができない（手動でバックアップする）

### 1.3 基本方針
1. **記録は撮るだけ**：写真を撮れば、料理名・量・栄養価をAIが推定して保存します。修正は後からできます。
2. **AIがなくても記録できる**：よく食べるものの登録（ワンタップで記録）と手入力を用意し、通信できないときや無料枠を使い切ったときも記録を続けられるようにします。
3. **数値の計算はアプリが行う**：目標・残り・不足と超過の計算は、AIを使わずにアプリの中で行います。AIは「料理の推定」と「提案の文章」だけを担当します。こうすることで、計算結果が毎回ぶれず、オフラインでも数値を確認できます。
4. **送る情報は最小限にする**：AIに送るのは、写真（縮小し、撮影場所などの情報を消したもの）、入力した文章、提案に必要な数値だけです。名前などの個人を特定できる情報は送りません。
5. **サーバーを持たない**：記録は端末内（ブラウザの保存領域）にだけ保存します。ファイルへの書き出し・読み込みでバックアップします。
6. **AIは差し替えられる作りにする**：将来、有料のAI（Claude APIなど）に切り替えられるよう、AIを呼び出す部分を分けて作ります。

## 2. 用語定義

| 用語 | 意味 |
|---|---|
| PWA | ホーム画面に追加して、アプリのように使えるWebアプリ |
| Gemini API | Googleが提供するAIを、アプリから呼び出すためのしくみ。写真と文章を送ると、AIの回答が返ってくる |
| APIキー | Gemini APIを使うための合言葉のような文字列。Google AI Studio（GoogleのWebサイト）で自分で発行する。他人に知られると、自分の無料枠を勝手に使われる |
| 無料枠 | Gemini APIを無料で使える範囲。1分あたり・1日あたりの回数に上限がある |
| 食事 | 1回の食事（朝食・昼食・夕食・間食のどれか）。1つの食事に、複数の品目を記録できる |
| 品目 | 食事に含まれる料理や食品の1つ1つ（例：「白ごはん 150g」「味噌汁 1杯」） |
| よく食べるもの | 品目を、名前と栄養価ごと登録しておいたもの。ワンタップで記録できる |
| 栄養価 | 本アプリで管理する6項目：エネルギー（カロリー）、たんぱく質、脂質、炭水化物、食物繊維、食塩相当量 |
| PFC | たんぱく質（Protein）・脂質（Fat）・炭水化物（Carbohydrate）の3つ |
| 基礎代謝 | 何もせずに横になっていても使われるエネルギー（kcal/日） |
| 活動係数 | 1日の活動量の多さを表す数値。基礎代謝に掛けて、1日に必要なエネルギーを求める |
| 目標 | 1日に摂るべきカロリーと栄養素の量。計算方法は3.5 |
| 記録日 | 食事を数える日。午前4時（設定で変更可）までの食事は前日の記録として数える（3.1） |
| アクティブエネルギー | iPhoneのヘルスケアに記録される、体を動かして使ったエネルギー |
| ショートカット | iPhone標準の「ショートカット」アプリ。ヘルスケアからの値の取り込みに使う |
| 提案 | AIが作る、次の食事のおすすめや、翌日の調整案の文章 |
| バックアップファイル | アプリの全データを1つのファイル（JSON形式）にまとめたもの。復元に使う |

## 3. 機能要件

優先度：**Must**＝フェーズ1で必須／**Should**＝フェーズ1で可能なら実装／**Could**＝余裕があれば実装／**Future**＝将来対応

### 3.1 食事の記録

| ID | 要件 | 優先度 |
|---|---|---|
| F-REC-01 | ホーム画面の「撮影」ボタンでカメラを起動し、撮った写真をAIで読み取って食事を記録する（3.2） | Must |
| F-REC-02 | カメラの代わりに、端末に保存済みの写真を選んで記録できる | Must |
| F-REC-03 | 文章で入力した内容（例：「牛丼並盛と味噌汁」）をAIで読み取って記録できる（2026-11-07 決定） | Must |
| F-REC-04 | よく食べるもの（3.4）を選んで、ワンタップで記録できる。AIは使わない（2026-11-07 決定） | Must |
| F-REC-05 | 品目の名前と栄養価を手で入力して記録できる。AIは使わない | Must |
| F-REC-06 | 食事の区分（朝食・昼食・夕食・間食）を、記録した時刻から自動で決める。区分は記録の前後に変更できる。初期の区切り：4:00〜10:59 朝食、11:00〜14:59 昼食、15:00〜16:59 間食、17:00〜翌3:59 夕食 | Must |
| F-REC-07 | 食べた日時は記録した時刻を初期値とし、変更できる（食べたあとで記録する場合のため） | Must |
| F-REC-08 | 保存済みの食事と品目を、編集・削除できる。品目の追加・削除、量の変更ができる。量を変えたら、栄養価を同じ割合で計算し直す | Must |
| F-REC-09 | 1つの食事に、写真・文章・よく食べるもの・手入力の品目を混ぜて記録できる（例：写真で読み取ったあと、飲み物をよく食べるものから足す） | Should |
| F-REC-10 | 「前回と同じ」で、同じ区分の前回の食事をまとめて記録できる | Could |

- **記録日の原則**：午前4時（設定で変更可）より前に食べた食事は、前日の記録として数えます（2026-11-07 決定）。例：11月8日 1:30 の夜食は、11月7日の記録です。目標との比較、カレンダー、グラフ、提案の集計はすべてこの原則に従います。
- 記録日の区切りの時刻を設定で変えた場合は、過去の記録も新しい区切りで数え直します（記録には食べた日時だけを保存し、記録日は表示のたびに計算するため）。

### 3.5 目標の計算

1日の目標は、次の手順で計算します（2026-11-07 決定：基礎代謝×活動係数をもとに、目的に応じて増減する）。式の細部（どの基礎代謝の式を使うか、係数の初期値）は、本書を作るときに補った**仮定**です。

**① 基礎代謝（kcal/日）**：国立健康・栄養研究所の式（日本人を対象に作られた式）を使います。

```
男性：（0.0481 × 体重kg ＋ 0.0234 × 身長cm − 0.0138 × 年齢 − 0.4235）× 1000 ÷ 4.186
女性：（0.0481 × 体重kg ＋ 0.0234 × 身長cm − 0.0138 × 年齢 − 0.9708）× 1000 ÷ 4.186
```

**② 基本の目標カロリー（kcal/日）**＝ 基礎代謝 × 活動係数 ＋ 目的による増減

| 項目 | 選べる値（初期値は太字） |
|---|---|
| 活動係数 | 日常生活の活動量から選ぶ（運動の分は③で足すため、運動は含めずに選ぶ）。低い：**1.50**／ふつう：1.75／高い：2.00（「日本人の食事摂取基準」の身体活動レベル） |
| 目的による増減 | 減量：**−500kcal**／維持：±0kcal／増量：＋300kcal（設定で変更可） |
| 下限 | 目標カロリーは基礎代謝を下回らないようにする。下回る場合は基礎代謝の値にし、その旨を表示する |

**③ 運動の上乗せ（kcal）**＝ 0 と（その日のアクティブエネルギー − 普段のアクティブエネルギー）の大きいほう

- アクティブエネルギーには、運動だけでなく日常の歩行なども含まれます。活動係数ですでに見込んでいる分と重ならないよう、「普段のアクティブエネルギー」（初期値300kcal、設定で変更可）を超えた分だけを足します。
- アクティブエネルギーを取り込んでいない日は、上乗せは0です。

**④ その日の目標カロリー**＝ ② ＋ ③

**⑤ 栄養素の目標**
| 栄養素 | 目標 |
|---|---|
| たんぱく質 | 体重kg × **1.6** g（筋力トレーニングをしている人の目安。係数は設定で変更可） |
| 脂質 | 目標カロリーの **25%** ÷ 9（g）（割合は設定で変更可） |
| 炭水化物 | （目標カロリー − たんぱく質g × 4 − 脂質のkcal）÷ 4（g）。残りをすべて炭水化物とする |
| 食物繊維 | 「日本人の食事摂取基準（2025年版）」の目標量（性別・年齢別）以上 |
| 食塩相当量 | 「日本人の食事摂取基準（2025年版）」の目標量（性別・年齢別）未満 |

**端数の処理**：計算の途中では端数を残し、表示するときに、カロリーは1kcal単位、PFCと食物繊維は1g単位、食塩相当量は0.1g単位に四捨五入します。基礎代謝は、1kcal単位に四捨五入した値を②で使います。

**計算例**（男性・35歳・身長172cm・体重70kg・活動係数1.50・減量）
| 手順 | 計算 | 結果 |
|---|---|---|
| ① 基礎代謝 | （0.0481×70 ＋ 0.0234×172 − 0.0138×35 − 0.4235）× 1000 ÷ 4.186 ＝ 1549.28… | 1,549kcal |
| ② 基本の目標 | 1,549 × 1.50 − 500 ＝ 2,323.5 − 500 → 2,324 − 500 | 1,824kcal |
| ③ 運動の上乗せ | アクティブエネルギー520kcalの日：520 − 300 | 220kcal |
| ④ その日の目標 | 1,824 ＋ 220（運動しなかった日は1,824） | 2,044kcal |
| ⑤ たんぱく質 | 70 × 1.6 | 112g |
| ⑤ 脂質 | 1,824 × 0.25 ÷ 9 ＝ 50.67… | 51g |
| ⑤ 炭水化物 | （1,824 − 112×4 − 456）÷ 4 ＝ 920 ÷ 4 | 230g |

（参考：女性・30歳・身長158cm・体重55kgの基礎代謝は、1184.40… → 1,184kcal）

| ID | 要件 | 優先度 |
|---|---|---|
| F-TGT-01 | 上の式で、記録日ごとの目標を計算する | Must |
| F-TGT-02 | 計算に使う体重は、その記録日以前で最も新しい体重の記録とする（3.8）。体重を記録し直すと、それ以降の日の目標が変わる | Must |
| F-TGT-03 | 目標の値を、計算ではなく自分で直接入力して上書きできる（項目ごと） | Should |
| F-TGT-04 | 目標の画面に、計算の内訳（基礎代謝、活動係数、目的による増減、運動の上乗せ）を表示する | Should |
| F-TGT-05 | 目標は一般的な目安であり、医療的な助言ではないことを明記する | Must |

### 3.8 体重

### 3.9 ヘルスケアからの取り込み（ショートカット経由）

Webアプリはヘルスケアのデータを直接読めません。また、ホーム画面から開いたPWAは、ショートカットからURLで呼び出すとSafariのタブで開いてしまい、データの保存場所が別になります（training-appの基本設計書 6.5 で確認済み）。そこで、次の方式をとります（2026-11-07 決定：アクティブエネルギーをショートカット経由で受け取る。方式の細部は本書を作るときに補った**仮定**）。

**取り込みの流れ（案）**
1. アプリの「運動を取り込む」ボタンを押す
2. ショートカットアプリが起動し、その日のアクティブエネルギーの合計をヘルスケアから読み取って、クリップボードにコピーする
3. 画面左上の「◀（戻る）」でアプリに戻る
4. アプリの「貼り付け」ボタンで値を取り込む

| ID | 要件 | 優先度 |
|---|---|---|
| F-HLT-01 | 上の流れで、記録日ごとのアクティブエネルギー（kcal）を取り込む。同じ記録日に取り込み直したら、新しい値で上書きする | Must |
| F-HLT-02 | アクティブエネルギーを手で入力することもできる（ショートカットを使わない場合や、うまく動かない場合のため） | Must |
| F-HLT-03 | ショートカットの導入手順を説明する画面を用意する（配布用のショートカットのリンク、または作り方の手順） | Must |
| F-HLT-04 | 連携のオン・オフを設定で切り替えられる。オフのときは「運動を取り込む」ボタンを表示しない | Must |
| F-HLT-05 | 記録日の区切り（午前4時）とヘルスケアの日付（0時区切り）の違いを扱う。ショートカットは「記録日の4:00から翌日の3:59まで」の値を読み取る（ショートカットで時間の範囲を指定できるかは要確認。未決事項No.2） | Should |

## 5. 非機能要件

| 分類 | 要件 |
|---|---|
| 使いやすさ | アプリを起動してから2タップ（「撮影」→ シャッター）で、写真での記録を始められる。よく食べるものは3タップ以内（「追加」→「よく食べるもの」→ 品目）で記録できる。片手で操作できる。ダークモードに対応する。iPhoneの画面上端・下端の領域（ノッチやホームバー）と表示が重ならない |
| アプリらしさ | ホーム画面に追加すると、ブラウザのアドレスバーなしの全画面で起動する。アプリのアイコンと起動画面を用意する |
| 性能 | 起動から3秒以内に操作できる状態になる。画面の切り替えやボタンの反応は1秒以内。AIの読み取り中は進み具合を表示し、30秒たっても回答がなければ中断して、もう一度試すかを選べるようにする |
| AIの呼び出し回数 | 無料枠の範囲で使えるよう、1回の記録で呼び出すAIは原則1回にする（推定と提案をまとめる）。写真は読み取りに必要な大きさまで縮小して送る |
| オフライン | 一度読み込んだあとは、通信がなくても起動・記録（よく食べるもの・手入力）・閲覧ができる（Service Workerによるキャッシュ） |
| 更新 | 新しい版を公開したら、次回起動時に更新を知らせ、ワンタップで適用できる |
| 信頼性 | 保存処理の途中で失敗した場合は保存前の状態に戻す。AIの読み取りに失敗しても、撮った写真を失わない（もう一度読み取れる）。データ構造を変更するときは、既存データを自動で新しい形式に移行する |
| セキュリティ | HTTPSで配信する。APIキーは端末内にだけ保存し、ソースコードやバックアップファイルに含めない。AIに送る内容は1.3の方針4に従う。外部の解析ツールや広告は組み込まない |
| 可用性 | 記録データは端末内にあるため、サーバーの稼働率は要件として定めない。AIの機能は、Gemini APIが使えるときだけ使える |
| 拡張性 | AIを呼び出す部分を分け、ほかのAI（Claude APIなど）に差し替えられるようにする。クラウド同期に、データ構造を大きく変えずに対応できる |
| 保守性 | 計算ロジック（目標・集計・記録日）を画面の処理から分け、単体テストができる構造にする。AIへの指示文（プロンプト）は1か所にまとめる |

## 7. 制約事項・対象外

### 7.1 方式による制約

| 制約 | 影響と対策 |
|---|---|
| 無料枠では、送った内容がGoogleのサービスの改善に使われる | Gemini APIの利用規約では、無料枠で送った内容と回答は、Googleの製品の改善に使われ、人が内容を読む場合があるとされている（アカウントやAPIキーとの紐付けは外したうえで）。また、無料枠には「機密情報や個人情報を送らないこと」とある。そのため、送る内容を最小限にし（1.3の方針4）、初回案内と設定画面でこのことを説明する（F-SET-05）。気になる場合は、将来の有料のAIへの切り替えで対応する（2026-11-07 公式の規約で確認） |
| 無料枠の回数に上限がある | 上限の値はモデルごとに異なり、公式の料金ページには載っていない（Google AI Studio の画面で確認する）。1日あたりの回数は、太平洋時間の0時（日本時間の17時、夏時間の期間は16時）にリセットされる。上限に達したら、よく食べるもの・手入力で記録を続ける（F-AI-07） |
| 無料枠の条件やモデルは、Googleの都合で変わる | 2026年12月1日に一部のモデル（gemini-2.5-flashなど）が別のモデルに切り替わる予定がある（公式の料金ページより）。モデルを設定で変えられるようにする（F-AI-10）。無料枠がなくなった場合は、有料のAIへの切り替えを改めて検討する |
| APIキーを端末からGoogleに直接送る | Googleは、製品として配布するアプリでは、キーをブラウザ側に置かず中継サーバーを使うよう勧めている。このアプリは自分専用で、キーはソースコードに書かず、自分で入力して端末内だけに保存するため、この方式とする。キーには「Gemini API だけに使える」などの利用制限を付けるよう、設定手順の画面で案内する（F-KEY-03） |
| AIの推定は正確ではない | 写真から量を推定するため、誤差が出る。推定値であることを明記し（F-AI-09）、後から修正できるようにする |
| ヘルスケアのデータを直接読めない | ショートカットでクリップボードにコピーし、アプリで貼り付ける（3.9）。ホーム画面から開いたPWAは、ショートカットからURLで呼び戻せない（Safariのタブで開いてしまう） |
| iCloudで自動同期できない | バックアップファイルを手動で書き出す（3.12）。複数端末間の同期は将来対応 |
| データはブラウザの保存領域にある | **ホーム画面からアプリを削除すると、データも消える。** また、Safariのタブで開いた場合とホーム画面から開いた場合では、データの保存場所が別になる。必ずホーム画面から使うよう、初回案内で説明する |
| アプリのURLにリポジトリ名が含まれる（GitHub Pages） | **GitHubのリポジトリ名（Track-my-meals）を変更しない。** 変更するとURLが変わり、ホーム画面に追加したアプリが開けなくなる。端末内のデータも新しいURLからは読めなくなる |
| 同じドメイン（ryotasg24.github.io）のほかのサイトと保存領域を共有する | training-appなど、GitHub Pagesで公開するほかのサイトとは、ブラウザの保存領域が共有される。データの衝突を防ぐため、保存領域の名前（データベース名など）には、このアプリ専用の接頭辞を付ける。APIキーも同じドメインのほかのサイトから読める状態になるため、同じドメインには信頼できる自作のサイトだけを置く |
| プッシュ通知を使わない | 体重の記録やバックアップの催促、ふりかえりは、アプリを開いたときに画面上で知らせる |
| 写真の保存で容量を使う | 縮小した写真だけを保存して、容量とバックアップファイルの大きさを抑える（F-AI-05） |

### 7.2 対象外
- ユーザー登録・ログイン機能は作りません。
- 他人とのデータ共有、SNSへの投稿は対象外です。
- 持病・アレルギー・妊娠中などによる食事の制限は考慮しません（2026-11-07 決定）。目標と提案は一般的な目安であり、医療的・栄養学的な助言ではありません。
- 栄養価6項目以外（ビタミン、ミネラル、糖質、水分など）は管理しません。
- 商品のバーコードの読み取りは対象外です。
- 筋トレ記録アプリ（training-app）とのデータの直接の連携は行いません。運動の分は、ヘルスケアのアクティブエネルギーから取り込みます（3.9）。
- Androidでの動作確認は行いません（PWAのため動く可能性はありますが、対象外とします）。
